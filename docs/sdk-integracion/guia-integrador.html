Guía completa para integradores

Esta es la entrada recomendada para integrar la candidata 0.1.0-rc.40. Una capacidad documentada sólo puede usarse cuando el ambiente figura ACTIVE y la combinación de journey/perfil aparece habilitada para tu integración.

Qué integra el cliente​

La integración tiene un SDK de servidor y un SDK de browser:

  1. Tu backend usa @lakaut/server para consultar elegibilidad, crear y consultar sesiones, verificar/custodiar el PDF y validar webhooks.
  2. Tu frontend usa @lakaut/browser para montar Hosted UI con la credencial efímera devuelta por el backend.

No llames directamente a la API privada de Auth ni implementes OTP, PIN, emisión o firma. La API key y el secreto webhook nunca llegan al navegador. Tu endpoint de creación de sesiones debe autenticar al usuario y autorizar la operación solicitada.

Qué entrega Lakaut​

ValorUsoSensibilidad

X-Integrator-IdUUID canónico de tu integración en ese ambienteidentificador, no secreto

El UUID se copia en Integradores → Mi integración → Empresa / contrato. No lo generes, no uses el slug y no lo obtengas desde el browser. Las credenciales se entregan o generan por un canal seguro y se guardan en el secret manager del backend.

El OTP del portal se envía al correo registrado del operador. Es distinto del OTP del titular dentro de Hosted UI, cuyos factores dependen del perfil de autenticación elegido.

Ambientes​

El enum público es local, sandbox y production:

DespliegueValor SDK
laboratorio locallocal
DEVsandbox
PREPRODsandbox
PRODproduction

DEV y PREPROD no comparten API keys, secretos webhook, orígenes ni autorizaciones aunque usen el mismo valor SDK. El código avanza local → DEV → PREPROD → PROD; la configuración se crea de forma independiente en cada ambiente.

Las URLs no se deducen de sandbox. Lakaut entrega la URL base server-side y cada sesión devuelve su hostedUiOrigin, que es la autoridad para CSP, frame-src, targetOrigin y event.origin.

El estado de la integración/ambiente y el del webhook son independientes:

Que el panel muestre DRAFT/“Borrador” no significa que el SDK esté en borrador: esa integración todavía no está operativa. Lakaut debe completar el flujo de provisionamiento y comprobar que termine en ACTIVE; no se corrige cambiando código del cliente.

ACTIVE no implica VERIFIED, ni al revés. Para depender del webhook deben cumplirse ambos.

Elegir el journey​

flowType es una cadena literal dentro de createSession() en tu backend:

flowTypeUso
PASSWORDLESS_AUTHautenticar sin emitir ni firmar
ONBOARDINGemitir certificado sin firmar
SIGNINGfirmar con un certificado vigente
ONBOARDING_AND_SIGNINGemitir cuando corresponda y luego firmar
const created = await sessions.createSession({
  flowType: "ONBOARDING_AND_SIGNING",
  allowedOrigin: process.env.LAKAUT_ALLOWED_ORIGIN,
  externalUserRef: req.user.id,
  email: req.user.email,
});

No se envía por query param ni desde el browser. flowType selecciona el objetivo; el perfil selecciona los factores. Los perfiles modelados son auth.email.v1, auth.sms.v1 y auth.email-sms.v1, sujetos al alcance de tu integración. El modo legado que sólo manda flowType usa auth.email-sms.v1; para otro perfil usá la combinación journeyId/authenticationProfileId publicada por getCatalog().

Certificado vencido o revocado​

Antes de crear una firma, tu backend puede ejecutar getSigningEligibility(). La respuesta recomienda SIGNING, ONBOARDING_AND_SIGNING, reintentar luego o contactar a Lakaut, sin revelar seriales ni permitir enumerar certificados.

Si mandás SIGNING directamente, la sesión puede crearse, pero después del OTP Lakaut revalida que exista un certificado de persona física vigente, válido, habilitado para firma y asociado a esa identidad. Un certificado vencido o revocado devuelve CERTIFICATE_REQUIRED: no solicita PIN, no firma y no cambia automáticamente a onboarding.

Orígenes y subdominios​

Cada sesión lleva un allowedOrigin HTTPS exacto, sin path, query ni fragmento. Para una aplicación multi-tenant, Lakaut puede registrar como patrón administrativo un único nivel de subdominio, por ejemplo https://*.apps.vafirma.com. Puede cubrir https://lakaut.apps.vafirma.com, pero no el dominio base, varios niveles, HTTP ni otro puerto.

El manager puede guardar ese patrón desde el formulario de autoservicio, una vez que Lakaut le asignó la integración y su alcance comercial. El wildcard nunca se manda en una sesión: allowedOrigin continúa siendo el origen concreto y literal. Tu backend debe resolverlo desde el tenant autenticado y validarlo contra su propia allowlist.

Firma visible y PDF​

La posición visible usa página basada en 1 y coordenadas enteras normalizadas de 0 a 1000, con (0,0) en la esquina superior izquierda de la página visible. Lakaut considera CropBox y rotaciones 0/90/180/270. Una geometría inválida devuelve INVALID_VISIBLE_SIGNATURE_PLACEMENT; no se corrige ni se mueve silenciosamente.

En la candidata 0.1.0-rc.40 de preproducción:

  • actualización incremental: soportada con una única revisión incremental;
  • preservación de firmas previas: soportada y validada;
  • PAdES B-B y B-T: soportados, con B-T condicionado a un timestamp RFC 3161 válido;
  • PAdES B-LT/B-LTA y material LTV: no soportados.

Estas capacidades corresponden al release y ambiente indicados. No deben extrapolarse a producción ni a una versión diferente del SDK.

Webhooks​

El endpoint vive en tu backend y debe conservar los bytes crudos. Hay dos firmas:

  • desafío de activación: t + "." + rawBodyBytes;
  • evento normal: t + "." + eventId + "." + rawBodyBytes.

El evento usa Lakaut-Signature: t=<timestamp>,v1=<hex> y exige también Lakaut-Event-Id, Lakaut-Event-Type, Lakaut-Event-Timestamp y Lakaut-Schema-Version. constructWebhookEvent() valida HMAC, igualdad de timestamps y una tolerancia de 300 segundos por defecto. Deduplicá por event.id, persistí primero en una inbox durable y respondé 2xx rápido.

Para auth.document.signed:

  • 1.1.0 contiene signedContentHash y conserva el carril compatible;
  • 1.2.0 requiere opt-in, custodia y binding; agrega finalPdfHash y se emite al quedar BOUND.

signedContentHash identifica el contenido autorizado para firma. finalPdfHash identifica los bytes finales que tu backend verificó, custodió y vinculó. El webhook no transporta el PDF. Una falla de custodia o entrega nunca autoriza una segunda firma.

Responsabilidades​

ActorResponsabilidad
LakautHosted UI, autenticación, emisión/firma, sesión, eventos y control plane
backend integradorproteger endpoints, mantener secretos, elegir journey, custodiar/verificar PDF e inbox idempotente
frontend integradormontar @lakaut/browser, entregar el PDF al backend y validar orígenes exactos
operador del portalmantener configuración por ambiente y completar activación/verificación

El evento del browser es una señal de UX, no la verdad final. Tu backend consulta estado y, en 1.2, espera el binding BOUND.

Soporte​

Compartí ambiente, hora aproximada, código público y correlationId; cuando corresponda, agregá sessionId, documentId o eventId. No envíes API keys, secreto/firma webhook, body crudo, PDF, CMS, OTP, PIN, email, teléfono ni otros datos personales.

Continuá con el Quickstart, Backend y sesiones, Documentos y firma, Eventos y estado y Errores. Para un alta nueva completá el Checklist de onboarding.
